# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## Domain interaction contract

- A top tab is one `ProductionPlan`, an independent planning document.
- A sidebar item is one `ProductionBlock`, an organization and isolation container. It does not own targets and does not jointly solve its Root Lines.
- Selecting a sidebar `ProductionBlock` switches the entire Block organization canvas. Root Lines are selected inside that canvas; they must not be rendered as sidebar navigation peers or nested sidebar destinations.
- A Block contains one or more Root `ProductionLine` objects. Every Root Line is an independent solve domain in the prototype.
- The primary planning canvas belongs to the selected `ProductionBlock`, not to a selected Root Line. It must keep every Root Line in that Block available in the same canvas and treat Line selection as focus/inspection rather than a canvas replacement.
- The application hierarchy should read like a Finder window with Chrome-level tabs: `ProductionPlan` tabs are the highest visual navigation layer, the left sidebar is a deliberately simple `ProductionBlock` canvas switcher, and the center is the selected Block's multi-Line observation canvas.
- The Block canvas offers four interchangeable observations over the same Line/BOM instance data: a material rail, a DaisyDisk-style dependency ring, Finder-style drilldown columns, and an instance-preserving demand Sankey. Switching views must not mutate solving state or remove other Root Lines from the Block-level context.
- The Sankey view is a strictly conserved workload decomposition, not a second material-rate diagram. Ribbon width uses one linear unit across the complete Root Line: in-domain machine-seconds per minute. At every process node, `total workload = local processing workload + sum(internal child-subtree workload)`; the complete bar is partitioned into contiguous source slots with no nonlinear scale, minimum data-band width, or artificial gaps. The amber terminal flow represents local processing. Raw or otherwise external boundary supply contributes zero in-domain machine workload and stays visible only as a thin dashed dependency guide. Repeated materials and their ribbons remain separate, Root Lines occupy independent lanes, and solve domains never converge. Each target sits at the left edge on the vertical centerline of its complete dependency tree; dependencies continue right while fanning above and below that center. Compact bars and labels must leave the conserved ribbons—not cards—as the primary visual signal.
- In the material rail, the stable top-left origin is the user-selected target item. It is the only material node in that graph. Every expanded node after it is a recipe instance; raw and bounded materials stay visible as input rows inside their consuming recipe card instead of becoming graph nodes.
- A material-rail recipe card owns the complete process contract: real recipe icon and name, every product on its left, every ingredient on its right, executions per minute, selected crafting machine, machine-slot module fill, beacon count and beacon module, effective speed/productivity, and exact/rounded machine demand. All capacities, slots, effects, ratios, and icons come from game-data and recompute the BOM immediately when configuration changes.
- Every material-rail card uses one fixed footprint, including the target item, recipe instances, and co-product outputs. The target and its root recipe share the exact same top coordinate; their delivery connector is one horizontal line through both cards' vertical center.
- Every recipe-to-recipe demand remains an independent BOM and solve instance, including repeated materials. In the material-rail observation, all sibling edges leaving the same parent recipe share exactly one vertical trunk and one main connector leaving the parent card. Item and fluid material semantics remain on their demand metadata and card rows, but both use the same conveyor observation skin and the same trunk; the rail never draws a second pipe route. Each branch joins through the matching corner/T/cross topology tile, and ingredient rows never create parallel visual entrances.
- Connector routes contain no floating material or rate badges. The endpoint recipe cards own material identity, rate, and input/output semantics; the route itself stays visually clean and communicates only medium and topology.
- The material rail is a CSS Grid document-flow layout, not an absolutely positioned canvas. Cards span fixed grid tracks and connector tiles are real grid items, so cards, routes, depth, and sibling rows jointly determine the scrollable surface.
- Conveyor connectors use 40px square raster tiles on that shared grid rather than stretched line backgrounds or floating overlays. One reusable `TransportTile` consumes a four-bit N/E/S/W state (`0–15`) and chooses the matching atlas cell; the topology set therefore covers isolated, straight, corner, endpoint, T, and four-way crossing states without state-specific layout code. Every tile has one immutable horizontal and vertical port axis. Straight and junction arms are constant-width corridors centered on those axes. A corner uses a compact, game-authored 90-degree round elbow: its outer shell may have a broader radius than its tight inner corner, but its entry and exit leads must land tangentially on the immutable horizontal and vertical axes. The source artwork is fitted by measuring its two port centers, after which every open edge is overwritten with the same canonical centered port strip used by straight tiles. Rotating or scaling the visual body may never move either port off-axis. Closed edges expose no pixels, and arbitrary legal neighbors remain pixel-aligned and seamless.
- Material-rail connector spacing is expressed in whole transport cells: target item to root recipe is exactly one horizontal tile; adjacent recipe columns are separated by exactly three tiles. A parent aligned with its first child therefore reads `horizontal | T | horizontal`, while any later child branching from the existing vertical trunk reads `T | horizontal`. The vertical trunk starts at the first real junction and ends at the last real junction with no decorative overhang.
- Every visible conveyor tile remains a real hit-testable DOM element. Inspect and annotation tools must be able to select the rendered `TransportTile` directly and read its route owner, source material type, grid coordinate, transport skin, four-bit mask, topology, and N/E/S/W directions from stable `data-*` attributes; `display: contents` route wrappers must never make visible tiles pointer-transparent.
- Every non-demanded product of a recipe remains an objective co-product instance. Route it independently back to the left output column, vertically aligned with the target-output column, and label its source recipe and rate. Repeated co-products from different recipe instances never merge.
- In every material-rail subtree, the first direct child inherits its parent's vertical position. Repeating this rule creates one continuous horizontal primary path (for example target -> first input -> that input's first input); only the second and later sibling branches allocate rows below it.
- In Finder columns, the first column lists every Root Line in the Block, followed by target and per-level dependency columns; this column hierarchy is an observation of the Block, not a replacement navigation hierarchy for Plan or Block.
- A ProductionLine owns one production graph and one or more net-boundary delivery constraints. Multiple constraints in one Line describe one shared production network; they must never be placed on the Block.
- Plans and Blocks never prefill or own a target. Every newly initialized Root ProductionLine is a targetless draft; its first target is written only after the user confirms an entry and a rate in the target encyclopedia.
- The target encyclopedia combines visible `items` and `fluids` from `game-data.json`. Its group rail follows `item_groups.order`, subgroup navigation follows each group's `subgroups.order`, and entry cells follow the owning subgroup followed by each item/fluid `order`. It must use the corresponding real group, item, fluid, and recipe icons plus i18n names.
- Confirming a target automatically chooses a sensible default producing recipe and recursively expands its BOM until raw or explicitly bounded materials. Recipe selection is not a second target-selection step.
- Every expanded BOM process records the exact downstream material demand it fulfills. Replacing that process may only offer recipes that produce the same material; applying an alternative preserves the downstream rate and recalculates the upstream BOM, boundary inputs, byproducts, and machine counts.
- A second target can only be promoted from a material already produced by the current Line graph. Do not offer arbitrary global material search for this action.
- Internal child Lines express down-sunk local solve domains. `link = on` follows parent boundary demand; `link = off` exposes a user-controlled child target and must retain any gap or surplus.
- External inputs and exports remain explicit boundary declarations. Never auto-connect matching materials across Blocks or Plans.
- Recipe values, entity capacities, game object names, and icons come from `../assets/exported/game-data.json`, `../assets/exported/translations-*.json`, and `../assets/icons`.
- The main ProductionLine planning surface must use one generic, data-driven renderer. Derive stages, input flows, internal flows, outputs, and rates from recipe `ingredients`, `products`, and the solve result; never add recipe-specific canvases, hand-positioned nodes, or per-recipe blueprint artwork.
- Replacing a Line recipe from the real catalog must reuse the same topology renderer for every recipe, including multi-input and multi-output recipes. Results/debug panels stay secondary and default to collapsed so the production topology owns the main workspace.
- The main ProductionLine view must preserve BOM ownership. Never flatten processes into stage buckets as the primary planning surface, because stage grouping loses which upstream process fulfills which downstream demand.
- A multi-input recipe must show all direct inputs together as sibling branches. Selecting one sibling reveals that branch's complete upstream chain without hiding the existence, rate, or relationship of the other direct inputs.
- Every expanded branch must explicitly label its consumer (for example, `处理器 → 效能科技包`) and keep that parent-child relation in solve output data rather than reconstructing ownership from visual proximity.
- Never merge BOM demand instances merely because they reference the same material. Repeated materials remain separate nodes, separate arcs/rows/stations, and separate upstream expansions; recipe replacement is scoped to the selected instance path.
