# 异星工厂量化工具需求收束（MVP 前置版）

## 1. 文档目的

本文用于收束当前针对《异星工厂》量化工具的需求讨论结果。

目标不是直接定稿全部方案，而是先把当前已经明确的需求、核心概念、主要矛盾点与待决策项整理出来，形成一份可以持续迭代的需求主文档。后续所有新增想法，都可以在这份文档基础上继续补充。

本阶段重点不是功能堆砌，而是先找出一条能跑通闭环的主线，以便尽快确定 MVP 的交互范式与底层技术路线。

---

## 2. 产品定位

这是一个偏“工具型”的《异星工厂》量化工具，而不是简单的后台管理页面。

因此，设计重点不仅是“能算”，还包括：

- 可用性
- 易用性
- 美观性
- 功能丰度
- 可扩展性
- 对复杂生产关系的可表达性

当前阶段的核心任务，不是继续发散更多功能点，而是先把已有想法串成一条可落地的交互主线。

---

## 3. 当前已明确的核心需求

### 3.1 指定生产目标

用户首先需要指定一个生产目标，作为整次量化的起点。

这个目标本质上是整棵生产结构的根节点。用户至少需要指定：

- 目标产物
- 目标产量或目标速率

这是后续所有配方回推、依赖展开、设备估算与原料计算的起点。

### 3.2 以目标为根节点自动展开配方树

在用户选定目标后，系统应自动以该目标为根节点，递归展开上游依赖关系，形成一棵可分析、可编辑的配方树。

自动展开是默认起手式，用于快速把“我要做什么”转成“这东西怎么做、需要什么、还缺什么”。

### 3.3 初始展开严格隔离，不自动合并同类原料节点

在配方树首次展开时，应严格按照各自依赖关系生成独立节点。

即使两个不同分支都需要同一种物料，也不应在初始阶段自动合并。它们应分别保留在各自子树下。

这样做的目的，是先保留来源语义，避免一开始就丢失“这份原料到底是给谁用的”这一关键信息。

### 3.4 用户可手动干预节点展开方式

用户不能只被动接受系统给出的展开结果，还需要能对节点进行人工干预。

一个重要需求是：用户可以对某个节点“内嵌一层子方案”或“挂接一颗新的子树”，用来细化该节点的内部实现。

这意味着：

- 一个节点既可以被视为黑盒
- 也可以继续拆解为更细的内部生产结构

内嵌后，该外层节点是否还能继续向外展开，取决于内部子树展开到什么深度：

- 如果子树已经展开到采矿等原始资源层，则外层节点可以视为叶子节点
- 如果子树只展开到中间层，则外层节点仍可继续向外生长，其直接子节点以前述子树的叶子为起点继续展开

### 3.5 节点共享需要显式表达，而不是隐式合并

当两个不同分支、甚至不同层级的节点，本质上应共享同一供给来源时，系统不能把它们简单画成两个“长得一样的普通节点”，否则用户会误以为这是两个独立产线。

因此，需要支持“共享节点”机制。

推荐语义如下：

- 用户指定其中一个节点作为主节点（master）
- 其它位置不再保留独立实体节点
- 其它位置显示为引用主节点的幽灵节点（ghost / alias）

### 3.6 幽灵节点必须是叶子节点

幽灵节点只用于表达“此处引用主节点”，而不是一个可以继续独立展开的真实生产节点。

因此幽灵节点应具备以下约束：

- 固定为叶子节点
- 不再单独承载下游依赖
- 不再独立展开其原料链
- 其所有真实依赖与计算结果统一归属于主节点

这条约束非常重要，因为它可以在保留树状阅读体验的同时，明确表达“这里只有一个真实产线，其它地方只是引用”。

---

## 4. 当前讨论中已经暴露出的核心建模问题

### 4.1 “严格树”与“共享节点”之间的矛盾

只要允许两个父位置共享同一个真实供给节点，就已经不再是纯树结构。

从数据结构上看：

- 初始独立展开时，模型可视为树
- 出现共享节点后，更接近 DAG

但在 UI 表达上，如果仍然强行保留“所有节点都是普通树节点”的外观，就会导致用户误判。

因此，是否共享、如何共享、共享后如何表达，已经成为第一批必须正视的核心问题。

### 4.2 品质模块引入“多品质分流”问题

当用户给某个配方节点配置品质模块后，该节点不再只产出单一结果，而是可能同时产生多个品质层级的产物。

这会带来两个影响：

1. 图结构不再只是简单的“从目标往上游回推”
2. 解算单位不能只看“物品”，而必须升级为“物品 × 品质”

这说明品质系统不是简单的显示问题，而会直接影响：

- 图模型
- 解算模型
- UI 呈现方式
- 副产物处理方式

### 4.3 多品质产物的平行空间思路

当前已经提出一个可行方向：

- 主树负责目标生产主链
- 多品质分叉结果不强行塞回主树
- 分叉结果进入独立 Tab 或平行空间处理
- 未处理结果先归集到“最终输出区”
- 用户再决定是否为这些结果挂接消纳方案

这个思路的价值在于：

- 主树不会因为多品质分流而立即爆炸
- 用户认知负担更小
- 工具能形成“先生产，再治理副产物”的操作闭环

### 4.4 副产物消纳与原油处理问题

品质系统只是副产物问题的一类。

另一个更典型、也更麻烦的场景，是游戏中的原油处理：

- 某个配方同时产出主产物与副产物
- 副产物之间还可以继续转化
- 最终可能收敛为单一产物
- 也可能重新供给其它需求节点

这已经不只是“多品质分流”，而是“副产物转化网络”。

它的问题在于：

- 副产物不一定通过一步配方就能被消纳
- 可能需要多步转化
- 可能出现循环利用
- 可能最终仍有剩余输出

这类问题不能只理解成“某个输出如何吃掉”，而更像是一个需要整体平衡的治理网络。

### 4.5 循环利用会破坏 DAG 假设

只要真的允许副产物回流到前面的需求链中，图结构就不再是 DAG，而会变成一般有向图。

这直接引出两个层面的矛盾：

1. UI 是否允许出现环
2. UI 背后的渲染数据结构是否仍可维持 DAG

如果 UI 上的每个元素都与一个真实节点一一对应，且边由真实父子 / 依赖关系驱动，那么：

- UI 允许环
- 背后的渲染数据结构就必须允许环

也就是说，不能只在“显示层”假装有环，却要求背后的结构仍是 DAG。

### 4.6 UI 语义与解算语义并不天然一致

当前讨论已明确一个很重要的事实：

- UI 想表达的是用户看得懂的依赖、分叉、共享、回流
- 解算想表达的是物料平衡、配方次数、余量、缺口、稳态流量

这两套语义并不天然同构。

所以未来很可能需要考虑：

- UI 渲染结构一套
- 解算结构一套
- 两者之间建立可追踪映射

这是一个很大的设计分水岭。

## 5. 目前已经出现的主要交互方向

### 5.1 主树 + 输出区 + 消纳子树

为了避免 UI 主图直接出现回环，一个重要思路是：

- 主树只表达目标到上游的依赖展开
- 副产物不直接“回接”到原有节点
- 副产物先进入输出区
- 用户对输出区中的某个物品再选择一个消纳方案
- 系统从该输出物重新长出一棵新的子树

这样做的优点是：

- 主图仍然可以保持 DAG
- 回流关系不需要在主图中用一条闭环线直接表达
- 用户可以把副产物治理理解为“后续处理链”

### 5.2 引用叶子而非真实回边

另一个方向是：即便某个副产物最终服务于前面某个需求节点，UI 也不直接画一条线接回原节点，而是在需求侧显示“此处由某个外部输出供给”或“引用某个处理结果”。

这种方式的特点是：

- 语义上表达了回流
- 结构上仍尽量避免形成真实环
- 用户看到的是“引用关系”，而不是几何意义上的回环

### 5.3 分层 / 分 Tab 表达复杂关系

复杂问题可以通过多层视图或多 Tab 拆分：

- 主生产树
- 品质分流空间
- 副产物处理空间
- 回收 / 循环利用空间

每个空间内部尽量保持结构可读。

真正复杂的循环关系，不一定非要压到一个平面主图里直接表现。

## 6. 主视图渲染方式：当前最大选型问题

当前最大、最直接影响技术栈的选型问题，是主视图到底采用哪种渲染范式。

### 6.1 方案 A：自由画布（Canvas / 无限画布）

特点：

- 可缩放
- 可平移
- 可拖拽节点
- 可自由摆放
- 更接近蓝图编辑器体验

优点：

- 自由度高
- 视觉表现力强
- 容易做出“工具感”“蓝图感”
- 容易支持复杂图形总览

缺点：

- 技术复杂度显著更高
- 需要处理缩放、平移、拖拽、自动布局、重排、连线路由等问题
- 会把大量工程成本消耗在“怎么画、怎么交互”上
- 对 MVP 非常不友好

### 6.2 方案 B：受控布局伪 Table / 树表混合视图

特点：

- 节点位置主要由系统决定
- 用户重点操作内容、关系、展开、合并、引用与参数
- 结构阅读性更强
- 更接近工具型工作台

优点：

- 更适合先做复杂语义闭环
- 更容易支持展开、折叠、共享、ghost 节点、输出区与子方案
- 易于在一行中同时放入数值、状态、操作入口
- 更适合 MVP 阶段快速跑通流程

缺点：

- 自由度不足
- 蓝图感较弱
- 后期若要做复杂总览，可能还需要额外补一个画布视图

### 6.3 当前倾向

当前讨论阶段，更倾向于：

- MVP 优先使用受控布局伪 Table / 树表混合视图
- 暂不把自由画布作为第一版主编辑界面
- 自由画布可考虑在后期作为总览视图、演示视图或高级模式补充

---

## 7. 主布局方向：当前建议

如果采用受控布局方案，主布局方向也需要尽快定型。

当前更建议：

- 根节点居左
- 主链向右展开
- 层级按从上到下方式排布

这样做的理由是：

- 更符合工具型界面的扫描式阅读习惯
- 更像依赖展开与数据流方向
- 便于后续在节点旁增加参数列、状态列、余量列、按钮区
- 比“根居中向左右发散”更适合作为工作台主界面

“根居中、左右对称分叉”更像一张展示图，而不太像长期高频使用的生产工具编辑界面。

---

## 8. 当前已识别出的关键待决策项

以下问题已经足以决定第一版 MVP 的实现路径。

### 8.1 主编辑视图到底是自由画布，还是受控树表

这是当前最重要的工程选型问题。

它会直接决定：

- 渲染方式
- 布局方式
- 连线方式
- 交互方式
- 技术栈选择
- 后续状态管理复杂度

### 8.2 UI 主图是否必须始终保持 DAG

这是当前最重要的数据结构与交互约束问题。

如果要求主图始终保持 DAG，则需要明确采用：

- 输出区
- 消纳子树
- 引用叶子
- 分层 / 分 Tab 表达

等交互方式，避免真实回边出现。

如果允许 UI 主图出现环，则渲染层背后的结构必须从一开始按一般有向图设计。

### 8.3 共享节点机制如何正式落地

虽然已经形成了“master + ghost”的方向，但仍需继续明确：

- 如何选择主节点
- 是否允许后续切换主节点
- ghost 节点的视觉样式如何定义
- 点击 ghost 时如何跳转到 master
- hover、选中、高亮、连线联动如何表现

### 8.4 品质系统的解算方式如何定义

目前还没有完全明确：

- 品质解算是否按期望值计算
- 不同品质是否作为独立物品状态参与全局平衡
- 多品质分流在 UI 中如何展示而不破坏主视图可读性

### 8.5 副产物消纳建模方式如何确定

目前至少存在两类方向：

- 把副产物视为输出区中的待处理物，再挂接消纳方案
- 把副产物视为可形成循环与整体平衡的网络结构

这会显著影响：

- UI 组织方式
- 用户操作路径
- 解算器建模方式

### 8.6 UI 数据结构与解算数据结构是否要彻底分离

如果两者分离，需要继续明确：

- 哪些节点是 UI 专属节点
- 哪些节点是解算语义节点
- 两者的映射粒度是什么
- 连线与变量、约束之间如何互相追踪

## 9. 当前建议的 MVP 主线

基于目前讨论，推荐先以“降低建模与实现风险”为前提，收敛出一条可落地的第一版主线。

### 9.1 MVP 推荐目标

先跑通以下闭环：

1. 用户指定目标产物与目标速率
2. 系统自动展开主生产树
3. 初始展开不自动合并同类节点
4. 用户可对节点进行局部细化 / 内嵌子方案
5. 用户可手动指定共享节点，形成 master + ghost 结构
6. 主树中的副产物先进入输出区，而不是立即回流
7. 用户可从输出区为某个副产物挂接消纳子树
8. 系统至少能表达：主产线、共享节点、输出区、消纳链

### 9.2 MVP 暂时可以不做的内容

以下内容不必在第一版全部解决：

- 自由画布式蓝图体验
- 真实回环图的完整渲染
- 完整的多品质全局平衡
- 高级副产物循环网络自动求解
- 所有复杂场景的一次性统一建模

### 9.3 MVP 先解决的不是“最终最优”，而是“先能跑通”

第一版更重要的是：

- 把用户交互路径跑通
- 把节点语义定义清楚
- 把主视图形态定下来
- 把后续可扩展的骨架搭起来

只要这些问题先稳住，后续无论是补品质系统，还是补复杂副产物循环，都会容易很多。

---

## 10. 当前建议的设计原则

### 原则 1：先保证语义清晰，再追求视觉自由

不要为了追求“蓝图感”而过早进入高复杂度渲染方案。

### 原则 2：默认先分开，再允许用户决定是否合并

自动系统不要一开始替用户做太多“智能合并”，否则会损失可解释性。

### 原则 3：共享关系必须显式表达

只要共享，就必须让用户一眼看出“这是同一个真实节点”。

### 原则 4：副产物优先视为待治理输出，而不是强行即时回流

这有助于保住主图的结构稳定性，也有助于降低用户理解成本。

### 原则 5：MVP 优先做受控布局主界面

在主要建模问题还未定型前，不建议把自由画布作为第一版核心路径。

---

## 11. 下一步建议

接下来最值得继续推进的，不是再发散更多点子，而是优先补齐以下几个决定性问题：

1. 最终是否确定 MVP 主视图为受控树表 / 伪 Table
2. 主图是否强约束为 DAG
3. 输出区与消纳子树的具体交互流程怎么走
4. master + ghost 的节点样式与交互规则怎么定义
5. 品质系统第一版是否先只做占位，不做完整闭环

只要这几个问题定下来，MVP 的骨架基本就能立住。

---

## 12. 当前一句话总结

当前这款量化工具的关键，不在于“功能还缺多少”，而在于：

**要先选出一种能承载复杂生产语义、又不至于把第一版实现拖入深坑的主交互范式。**

现阶段更推荐的方向是：

**以受控树表 / 伪 Table 为主视图，围绕“目标生产树 + 共享节点 + 输出区 + 消纳子树”先做出第一版 MVP。**
